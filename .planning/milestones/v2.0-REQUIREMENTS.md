# Requirements: v2.0 Multi-tenant Factory Architecture

**Milestone:** v2.0
**Archived:** 2026-04-22
**Status:** SHIPPED (with known gaps)

## v1 Requirements (Shipped in v1.0)

### Order Entry

- [x] **ORD-01**: Office staff can look up wholesale customer by code and see name instantly — Phase 1
- [x] **ORD-02**: Office staff can add products (ice bags by size) to an order with minimal keystrokes — Phase 1
- [x] **ORD-03**: Order total calculates automatically using customer's negotiated price list — Phase 1
- [x] **ORD-04**: Office staff can save and retrieve orders by customer or date — Phase 1

### Delivery

- [x] **DLVR-01**: Office staff can print a delivery slip from any order with one click — Phase 2
- [x] **DLVR-02**: Printed slip shows customer name, address, products, quantities, and total — Phase 2
- [x] **DLVR-03**: Printed slip includes a signature line for customer acknowledgment — Phase 2
- [x] **DLVR-04**: Slip prints correctly on A5 paper and thermal printers (80mm) — Phase 2
- [x] **DLVR-05**: Driver can open a URL on their phone and see today's delivery list — Phase 3
- [x] **DLVR-06**: Driver delivery list shows customer name, address, products, quantities — Phase 3
- [x] **DLVR-07**: Driver delivery list updates as new orders are added (refresh-based) — Phase 3
- [x] **DLVR-08**: Interface is dead simple — suitable for drivers with minimal tech literacy — Phase 3

### Inventory & Debt

- [x] **INVD-01**: Accountant can view a list of delivered slips returned by drivers at day end — Phase 5
- [x] **INVD-02**: Accountant can enter actual delivered quantity for each line item — Phase 5
- [x] **INVD-03**: System auto-deducts confirmed quantities from cold inventory after confirmation — Phase 5
- [x] **INVD-04**: Customer debt balance updates automatically after delivery confirmation — Phase 5
- [x] **INVD-05**: Owner can view daily debt report showing all outstanding customer balances — Phase 5
- [x] **INVD-06**: System tracks shell/bag deposits owed by each customer separately — Phase 5
- [x] **INVD-07**: Owner can see which customers owe deposits and how much — Phase 5

### Configuration

- [x] **CFG-01**: Products (ice types and bag sizes) can be configured in the system — Phase 1
- [x] **CFG-02**: Each customer has a price list with negotiated rates per product — Phase 1
- [x] **CFG-03**: Customer records include name, code, address, phone, and price list reference — Phase 1

## v2 Requirements (Multi-tenant Factory Architecture — v2.0)

### Factory Management

- [x] **FACT-01**: Factory can register with phone, name, email, password — Phase 02 ✓
- [x] **FACT-02**: Registration atomically creates User (ADMIN, isFactoryOwner=true) + Subscription (TRIAL, 14 days) — Phase 02 ✓
- [x] **FACT-03**: Tenant activation/deactivation via subscription status — Phase 01 ✓
- [x] **FACT-04**: 7-day grace period after cancellation (read-only), then locked — Phase 04 ✓

### Subscription

- [x] **SUB-01**: Trial subscription auto-created on factory registration (14 days) — Phase 02 ✓
- [x] **SUB-02**: Subscription enforcement — write operations blocked when TRIAL expired or PAID cancelled — Phase 02 ✓
- [x] **SUB-03**: Per-driver pricing — 1 admin free, paid per driver per month — Phase 02 ✓
- [x] **SUB-04**: Manual payment confirmation — Admin records payment, extends +30 days — Phase 03 ✓ (gap: no Payment record created)
- [x] **SUB-05**: VietQR content template for payment reference — Phase 03 ✓

### Super Admin

- [x] **SADM-01**: SUPER_ADMIN role above ADMIN — system-wide access, no factory filter — Phase 01 ✓
- [ ] **SADM-02**: Tenant list dashboard — all factories, subscription status, driver count, days remaining — Phase 03 ✓
- [x] **SADM-03**: Activate/deactivate tenant subscription from dashboard — Phase 03 ✓
- [x] **SADM-04**: Extend trial or subscription period (admin override) — Phase 03 ✓ (gap: audit log empty — no Payment writes)
- [x] **SADM-05**: Set price per driver — Phase 03 ✓

### Data Layer (Cross-cutting)

- [x] **DATA-01**: Add factoryId to Customer, Driver, Order, Product (and backfill existing records) — Phase 01 ✓
- [x] **DATA-02**: Prisma tenant middleware auto-injects factoryId into all queries via `$extends` + AsyncLocalStorage — Phase 01 ✓
- [x] **DATA-03**: Super Admin queries bypass factoryId filter (SUPER_ADMIN role flag) — Phase 01 ✓
- [x] **DATA-04**: Middleware enforces subscription status on every write request (403 if inactive) — Phase 01 ✓
- [x] **DATA-05**: Unique constraints are factory-scoped — e.g. Customer.code is unique only within a Factory — Phase 01 ✓

### Integration (v1.0 existing features)

- [x] **INT-01**: All v1.0 entities properly factory-scoped — Phase 04 ✓
- [x] **INT-02**: Per-customer pricing works within factory scope — Phase 04 ✓
- [x] **INT-03**: RBAC middleware extended with SUPER_ADMIN bypass — Phase 04 ✓
- [x] **INT-04**: Delivery slips filtered by factory (via order.factoryId) — Phase 04 ✓
- [x] **INT-05**: Driver web-view scoped to factory (via driver.factoryId) — Phase 04 ✓

## Known Gaps

| ID | Description | Severity | Fix |
|----|-------------|----------|-----|
| SUB-04 | PaymentRecorder calls /api/payments/confirm which extends subscription but does NOT create a Payment record. Audit log (SADM-04) will show empty table. | Medium | Add `prisma.payment.create()` in confirm endpoint |
| SADM-04 | Same as SUB-04 — audit log has no data because no Payment records are written | Medium | Same fix as above |
| — | SUPER_ADMIN blocked from /api/orders GET — breaks impersonation read | Medium | Add SUPER_ADMIN to allowed roles for GET |
| — | `factoryId: session.factoryId \|\| session.userId` fallback is semantically wrong (userId != factoryId) | Minor | Return 401 if factoryId is null for non-SUPER_ADMIN |
